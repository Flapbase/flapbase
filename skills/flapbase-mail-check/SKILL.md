# メールの届きやすさを診断する

## 用意するもの

持ち主（事業の判断をする人）から、会社・お店のメールアドレスのドメイン（@より後ろの部分）だけを受け取って始める。メールアドレス全体やパスワードは受け取らない。AI だけで使え、Flapbase への登録や MCP の接続は要らない。

DNS は、ドメインについて公開されている設定。SPF は、メールを送ってよいサービスの一覧。DKIM は、送信サービスがメールに付ける電子署名。DMARC は、SPF と DKIM の結果をどう扱うかを受け取る側に伝える、なりすまし対策の方針。SPF と DKIM は入っていても DMARC だけがないドメインが多いので、DMARC は必ず個別に確かめる。MX からは受信メールの契約先が、NS からは DNS を管理している会社が推測できる。この診断で分かるのは公開されている設定だけで、実際にメールが届くかどうかまでは確認できない。

## 始める前に

前の診断があれば、そのとき照会した名前・種類・URL・確認日時と比べる。なければドメインから始める。メールを送るサービスと受信の契約先は同じとは限らない。NS だけでは、契約の窓口や、別の会社が代わりに管理しているかどうかまでは分からないので、分からない点は「要確認（未確認）」にする。

## 手順

### 聞くこと

質問は一度に1つだけ。前の答えや DNS で分かったことは聞かない。分からないことは「未確認」のまま進める。

1. 会社・お店のメールアドレスのドメインは何か。
2. お客さまへのメールを、どのサービスから送っているか（Google Workspace・Microsoft 365・サーバー会社のメール・予約システムや配信サービス。複数でもよい）。
3. DNS の管理画面に自分で入れるか。入れないときは、制作会社などに頼むための文を返す。

Web を読める AI は、DNS over HTTPS（Web 経由で DNS を調べる方法）で次の4つを読む。`example.jp` は、受け取ったドメインに置き換える。URL にメールアドレス全体を入れない。

- DMARC： https://dns.google/resolve?name=_dmarc.example.jp&type=TXT
- SPF： https://dns.google/resolve?name=example.jp&type=TXT
- NS： https://dns.google/resolve?name=example.jp&type=NS
- MX： https://dns.google/resolve?name=example.jp&type=MX

Web を読めない AI は、この URL を1つずつ持ち主に開いてもらい、表示された結果を貼り付けてもらって読む。どの名前・種類を、どの URL で、いつ照会したかを、表の根拠として残す。返事の Status が成功になっているかを確認し、Answer から、該当する種類の値を読む。TXT の値が1つのレコードの中で分割されているときは連結し、別のレコードとは混ぜない。通信の失敗や DNS のエラーは「要確認」にして、正常に照会できたうえで該当するレコードがなかった場合とは区別する。

DKIM は、署名を選ぶための名前（セレクター）がサービスごとに違う。ドメインだけでは調べ尽くせないので、見つからなかっただけで「不足」としない。メールを送るサービスの公式ヘルプで「DKIM を有効にする」手順を探し、持ち主がそのサービスの管理画面で確認した DNS の名前・種類・公開値だけを使う。秘密鍵は受け取らない。指定された `<セレクター>._domainkey.<署名のドメイン>` を、同じ方法で TXT または CNAME として照会し、CNAME の場合は、その接続先の公開値も確かめる。

### 結果の形

毎回、次の表と「入れる値」、最後にその日のうちにできる「先にやる1つ」を返す。

| 見る点 | 見たこと | 判定（あり／不足／要確認） |
| --- | --- | --- |
| SPF | 公開の TXT の実値・許可された送る元・照会の根拠 | あり／不足／要確認 |
| DKIM | サービスごとの指定名と公開値。名前が不明なら未確認 | あり／不足／要確認 |
| DMARC | _dmarc の TXT の実値・照会の根拠 | あり／不足／要確認 |
| MX（契約先） | 公開の MX の実値と契約先の手がかり | あり／不足／要確認 |
| NS（DNS の管理先） | 公開の NS の実値と管理先の手がかり | あり／不足／要確認 |

「あり」は、公開の設定があり、確認できた範囲で矛盾がないことを示す。メールが実際に届くことまでは意味しない。SPF が複数ある、書き方が正しくない、メールを送るサービスとの関係が分からない、というときは「要確認」にする。DKIM は、メールを送るサービスごとに行を増やす。DMARC は、受信者に表示される差出人のドメインと、SPF または DKIM で認証されたドメインが一致している必要がある。実際の認証結果は公開の DNS だけでは分からないので、確認できていないものとして扱う。

**入れる値**（不足が確認できたものだけ。1レコードを1行で返す）：

| 種類 | 名前 | 値 |
| --- | --- | --- |
| TXT | _dmarc.example.jp | v=DMARC1; p=none |

上は DMARC がない場合の例で、実際には対象のドメインに置き換える。最初は `v=DMARC1; p=none` を入れる。これは「認証に失敗したメールを拒否してほしいとは求めない」という方針なので、この設定だけでなりすましが止まるわけではなく、メールが届くことを保証するものでもない。すでに DMARC があれば、そのまま残し、重複して追加したり、方針を上書きしたりしない。

SPF は、既存の行と、メールを送るサービスの公式の指定を確認し、既存の許可を残したうえで完成形を1行で返す。同じ名前の SPF の行を2つにしない。ほかの TXT は消さない。末尾の all や redirect の意味が変わってしまう単純な追記は避け、DNS の参照回数の上限（参照先を含めて10回）も確認する。完成形を決められないときは「要確認」とし、決まっていない値を入力用の表に入れない。サービスが別の送信用ドメインを指定している場合は、その指定に従い、受信用の MX は変更しない。

DKIM の値を自分で作らない。そのサービスの管理画面で「DKIM を有効にする」手順を探して進め、サービスからの指定が得られてから、種類・名前・値を表にする。案内では、NS から分かった管理会社の名前と、「DNS の設定」「DNS レコードの追加」のような一般的な言い方を使う。管理画面の操作名やメニューの名前は推測で書かず、分からないときは、その管理会社の公式ヘルプを持ち主と一緒に探す。名前の欄に短い形で入れるのか完全な形で入れるのかも、公式ヘルプで確認し、ドメインを二重に入力してしまうのを防ぐ。

自分で入力できない人には、次の依頼文を、診断の結果と入れる値の表を付けて返す。依頼文を送るのは持ち主。

> ドメインのメール設定の変更をお願いします。公開されている DNS の診断結果と、確認できた追加・更新の値を、下にまとめました。今のメールの送信元と受信の設定は変えず、SPF は同じ名前の行を1行にまとめてください。DKIM は、利用しているサービスの公式の指定を確認し、分からない値は入力せずに、私に確認してください。設定した名前・種類・値と、完了した日時を教えてください。

この文の下に、今回の2つの表を実際の値で添える。最後には必ず、「先にやる1つ」と、「入力したあとに、同じ URL をもう一度読んで、判定が『あり』になったかを確かめる」ことを書く。設定が反映されるまで待つ場合は、TTL（DNS が古い答えを保持する時間）を見て、あとで確かめ直し、続けて何度も照会しない。未確認の点が残っているうちは、完了にしない。

### 実行の例

以下は架空の DNS の応答と、その結果の例。ドメインも値も例であり、実際に測った値でも、入力の指示でもない。各表の根拠は「例の DNS 応答」。実際の診断では、照会した URL と確認した日時を付ける。

**コスメ（通販の注文確認と予約確認を、サーバー会社のメールから送る）**

渡されたもの：`example.jp`。送るサービスはサーバー会社のメール。DNS は自分で入力できる。公式の指定と、公開されている SPF が一致していた、という想定。

| 見る点 | 見たこと | 判定（あり／不足／要確認） |
| --- | --- | --- |
| SPF | 例：v=spf1 include:mail.example.com ~all | あり |
| DKIM | セレクターは未確認 | 要確認 |
| DMARC | 正常な応答に該当 TXT なし（例） | 不足 |
| MX（契約先） | 例：10 mail.example.com（サーバー会社） | あり |
| NS（DNS の管理先） | 例：ns1.example.com（代理管理の有無は未確認） | 要確認 |

入れる値（例）：

| 種類 | 名前 | 値 |
| --- | --- | --- |
| TXT | _dmarc.example.jp | v=DMARC1; p=none |

先にやる1つ：DNS の設定で、上の DMARC の1行を入力する。DKIM は、サーバー会社の公式ヘルプで、有効にする手順を確認する。
入力したあとに、同じ URL をもう一度読んで、判定が『あり』になったかを確かめる。DKIM は、確認できていないものとして区別したままにする。

**アパレル（Google Workspace＋配信サービス）**

渡されたもの：`example.com`。送るサービスは Google Workspace と配信サービス。DNS は自分では入力できない。この例では、両サービスの公式の指定を確認済みで、既存の SPF に配信サービスの許可だけが足りない、という想定。

| 見る点 | 見たこと | 判定（あり／不足／要確認） |
| --- | --- | --- |
| SPF | 例：v=spf1 include:_spf.google.com ~all。配信サービスの許可が不足 | 不足 |
| DKIM | 両サービスのセレクターは未確認 | 要確認 |
| DMARC | 例：v=DMARC1; p=none | あり |
| MX（契約先） | Google Workspace の公式指定と一致（例） | あり |
| NS（DNS の管理先） | 例：ns1.example.com。管理する会社は持ち主が確認済み | あり |

入れる値（既存の SPF を更新する例。DNS の参照回数が上限内だと確認した、という想定）：

| 種類 | 名前 | 値 |
| --- | --- | --- |
| TXT | example.com | v=spf1 include:_spf.google.com include:send.example.com ~all |

先にやる1つ：上の依頼文と2つの表を、制作会社に渡す。SPF は新しい行の追加ではなく、既存の1行の更新だと伝える。DKIM は、サービスごとに指定された値の確認を頼む。
入力したあとに、同じ URL をもう一度読んで、判定が『あり』になったかを確かめる。例にある send.example.com は架空のドメインなので、実際のサービスの指定値としては使わない。

**旅（予約システムから確認メール）**

渡されたもの：`example.org`。予約システムからメールを送っている。DNS は自分で入力できる。この例では、サービスの管理画面に専用の送信用ドメインの指定があり、必要な SPF は確認済み。DKIM 用の公開 CNAME が足りなかった、という想定。

| 見る点 | 見たこと | 判定（あり／不足／要確認） |
| --- | --- | --- |
| SPF | 専用の送信ドメインの TXT が公式指定と一致（例） | あり |
| DKIM | 例：booking._domainkey.example.org の CNAME がない。サービス指定値は確認済み | 不足 |
| DMARC | 正常な応答に該当 TXT なし（例） | 不足 |
| MX（契約先） | 例：10 mail.example.com。予約システムとは別のサービス | あり |
| NS（DNS の管理先） | 例：ns1.example.com。持ち主が管理先を確認済み | あり |

入れる値（例のサービスが指定した値、という想定）：

| 種類 | 名前 | 値 |
| --- | --- | --- |
| CNAME | booking._domainkey.example.org | booking-key.example.com |
| TXT | _dmarc.example.org | v=DMARC1; p=none |

先にやる1つ：予約システムの公式の手順に沿って、確認済みの DKIM の指定を DNS に入力する。続けて DMARC を追加する。
入力したあとに、同じ URL をもう一度読んで、判定が『あり』になったかを確かめる。DKIM がサービス側で有効になっているかの確認は、持ち主が行う。差出人の表示との一致や、メールが実際に届くかどうかは、この診断では確認できていない。

### 決まり

- 質問は一度に1つ。個人の情報を表に入れない。
- 何も送らない。読むのは公開されている DNS だけ（設定の手順は公式ヘルプで確認する）。メールは送らず、管理画面にもログインしない。判断と入力は持ち主が行う。
- 値を推測で作らない。DKIM の値・セレクター・管理画面の操作名を、自分で作らない。数も推測で埋めない。
- 最初から p=reject や p=quarantine を勧めない。今の設定を、断りなく弱めない。
- 設定が入っていることを、確かな効果があるとは言わない。成果は約束せず、迷惑メールに分類されないことや、メールが届くことも保証しない。

## チェックリスト

- 5つの見る点と、送るサービスごとの DKIM を、根拠を付けて表にした
- 照会のエラー・未確認・不足を区別した
- 入れる値は、公式の指定と今の設定に基づいていて、SPF が同じ名前で2行にならない
- DMARC の最初の値は p=none にし、すでにある設定は残した
- 自分で入力できない場合は、依頼文と今回の2つの表を返した
- 先にやる1つを決め、設定後に同じ URL でもう一度確認した

## 終わりの目安

持ち主が結果と入力する値を確認し、設定後に公開の DNS をもう一度読んで、対象が「あり」になった。DKIM は、メールを送るすべてのサービスの指定を確認し、サービス側で有効にしたことも持ち主が確認した。未確認の点や、反映待ちのものが残るときは、残っている点と次の確認方法を示して「確認待ち」とする。公開設定の診断が終わったことと、メールが実際に届くことは、区別して伝える。

## Flapbase で続ける

[Flapbase で開く](https://flapbase.com/skills/mail-check)。続けて見てもらうときは、伴走のエージェントに、診断の表・入れる値・未確認の点を渡す。予約システムや配信サービスを替えたときも、エージェントが同じ照会でもう一度確かめられる。結果は自動では送られず、何を渡すかは持ち主が決める。
