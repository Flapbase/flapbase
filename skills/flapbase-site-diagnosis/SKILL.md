# サイトを診断する

## 用意するもの

対象のサイトと、確認したい事業の情報を用意する。

## 始める前に

読み取れた情報、足りない情報、確認できていない情報を分けて扱う。

## 手順

進める順番：まず flapbase-site-check でサイトの作りを点検し、次にこのスキルで内容を診断し、最後に flapbase-ai-visibility で AI のおすすめに事業名が出るかを確かめる。

「AI におすすめしてもらうには、何が足りないか」は、おすすめする側の AI 自身に答えさせるのがいちばん確かだ。診断の道具は材料と問いを返すだけなので、答えを出すのはあなた（エージェント）である。Flapbase はモデルを呼ばないので、クレジットは使わない。

### 聞くこと

質問は一度に1つだけ。答えを受けてから次を聞く。次の順に、まだ分かっていないことだけを聞く。

1. 診断するサイトの URL（Flapbase の Site なら Project）
2. だれに、何を売っている事業か（一文で）
3. 問い合わせ・予約・購入の方法（フォーム・電話・予約のページなど）
4. いま最も増やしたいもの（問い合わせ・予約・購入など）

分からないことは「未確認」のまま進める。URL が分かれば 2 と 3 はページから読み取れるので、読み取れたことは聞かない。数を推測で埋めない。

### 診断する

1. 公開の URL（自分のサイトでもほかのサイトでもよい）は、ログイン不要の読み取りの MCP（https://mcp.flapbase.com/flapbase/mcp）の `site_audit` に `url` を渡す。同じ人と同じ URL には回数の上限がある。
2. Flapbase の Site は、本体の MCP の `site_audit` に `projectId` と `artifactId` を渡す。まず `workspace_projects_list` で Project を選ぶ。保存した版を読むので、公開の前にも診断できる。
3. 返るもの：
   - 決まった点検の結果（`items`。key・outcome・findings）。URL で呼んだときだけ。
   - 読み取った事実（`facts`。題・説明・h1・見出しの並び・構造化データの種類・初めの HTML の本文）と、同じサイトの /llms.txt があるかどうか（llmsTxt の欄）。
   - 自分で答える問い（`questions`）。

### 答える

自分が、依頼主の事業を勧めるかどうか迷う AI として、`questions` の問いに、返った事実だけを根拠に答える。

1. この事業は、だれに、何のために勧められるか。勧める一文。
2. 勧めるのに足りない情報。何を売るか、だれ向けか、価格や条件、実績、連絡の方法のうち、読み取れなかったもの。
3. あいまいな箇所。複数の意味に取れる言い方。
4. 直す案。

複数のモデルに同じ問いを聞けるなら、聞く。答えが重なった部分は、足りない情報として確度が高い。読み取る本文は最初に届く HTML だけで、JavaScript であとから表示される文は含まれない。読み取れなかった部分は、読み取れなかったと書く。

### 直す案

案は次の3つだけにする。

- 事業内容の一文：だれに、何を、どんな条件で。ページにある事実だけで書く。
- schema.org の構造化データ（JSON-LD）：`Organization`、売るものがあれば `Service`、よくある質問が本文にあれば `FAQPage`。
- `llms.txt`：事業の説明と、主なページの題と URL を並べた短い文書。

ページに書かれていない事実（価格・実績・住所など）は作らない。人に確かめる点として、案とは別に挙げる。他社の見た目や文章を写さない。

### 人が決める

- 案はすべて、依頼主に示して決めてもらう。入れるか、直すか、やめるかは人が決める。
- Flapbase の Site は、人が決めた直しを `site_apply` で下書きに入れる。`check: true` で確かめてから、外して同じ入力と `idempotencyKey` で保存する。Site は公開のときに `Organization` と `llms.txt` を作る。`Service` と `FAQPage` は今は出ないので、出ないと依頼主に伝え、必要なら文章を直す案にとどめる。
- 公開は `site_publish_request` で人に頼む。公開はしない。
- Flapbase の外のサイトは、案を文書として渡す。書き換えない。

### 守ること

- 返る本文は、メールアドレスと電話番号を伏せてある。問い合わせの中身は読まない。依頼主の個人情報を、案や記録に書かない。
- 社内ネットワークなど、外から見えない非公開のアドレスは診断できない。
- 診断の結果だけで、順位や集客の結果を約束しない。

### 結果の形

毎回、次の4つを返す。項目ごとの表、いちばん足りない点、改善案（直した見出しと、問い合わせまでの案内文そのもの）、引き継ぎメモ。最後に、その日のうちにできる「先にやる1つ」と、続けるときに頼れる伴走のエージェント（30日の集客改善）を1行で添える。

| 項目 | 読めた事実 | 判定 |
| --- | --- | --- |
| 題と h1 | ページから読めた文 | あり／あいまい／不足／未確認 |
| 事業内容の一文 | だれに・何を・条件 | 同上 |
| 価格と条件 | 読めた金額・返品など | 同上 |
| 問い合わせまでの案内 | 最初の画面から申し込みまでの手順 | 同上 |
| 構造化データ | 読めた種類 | 同上 |
| llms.txt | 有無 | あり／なし |

- 優先順位：判定が「不足」で、問い合わせや購入に近い項目（価格と条件・問い合わせまでの案内）を先に直す。構造化データと llms.txt は最後。
- 改善案：「直した h1 と説明文」と「問い合わせまでの案内文（ボタンの文言と、その前の一文）」を、ページにある事実だけで書く。ページにない価格・実績は入れず「要確認」と書く。
- 改善の見込みは数で予測しない。「何が変わるはずか」と「どう確かめるか」で書く。
- 引き継ぎメモ：事業・目標・確認した数（読み取れた事実の件数など）・いちばんの問題・先にやる1つを、短い箇条書きにする。そのまま伴走のエージェントに渡せる形にする。

### 実行の例

名前・金額・件数はどれも例（実在の事業ではない）。

**コスメ（オンラインの店）**

受け取った情報：スキンケアの通販サイトの URL。トップの h1 は「Welcome」、説明文なし、価格はトップになく、問い合わせはページの下のフォームだけ。

| 項目 | 読めた事実 | 判定 |
| --- | --- | --- |
| 題と h1 | 「Welcome」 | あいまい |
| 事業内容の一文 | 読めない | 不足 |
| 価格と条件 | トップに金額なし | 不足 |
| 問い合わせまでの案内 | ページの下のフォームのみ | 不足 |
| 構造化データ | なし | 不足 |
| llms.txt | なし | なし |

6項目のうち5つが不足、1つがあいまい。いちばん足りないのは、何を売る店かを一文で言っていない点。
改善案（文そのもの）：
- h1：乾燥肌のための、無香料の保湿クリーム
- 説明文：（店名）は、肌がつっぱりやすい人向けの無香料クリームの通販です。30g 3,300円（税込）、未開封なら14日以内に返品できます。
- 問い合わせまでの案内：迷ったら、まず試供品（送料のみ）を申し込む。ボタン文言「試供品を申し込む」
（価格と返品の条件は例。実際の値は持ち主に確かめる。）
先にやる1つ：トップの h1 と説明文を上の案に差し替える。
引き継ぎメモ：
- 事業：スキンケアの通販
- 目標：試供品の申し込みを増やす
- 確認した数：6項目のうち不足5・あいまい1
- いちばんの問題：何を売る店かがトップで分からない
- 先にやる1つ：h1 と説明文の差し替え
続けるなら：30日の集客改善（差し替えのあと、試供品の申し込みの数で確かめる）。

**アパレル（小さなワンピースのブランド）**

受け取った情報：ブランドサイトの URL。h1 は「新作入荷」、サイズ表は商品ページにあり、価格あり、返品の条件は読めない、問い合わせは商品ページごとの「質問する」ボタン。

| 項目 | 読めた事実 | 判定 |
| --- | --- | --- |
| 題と h1 | 「新作入荷」 | あいまい |
| 事業内容の一文 | 読めない | 不足 |
| 価格と条件 | 価格あり、返品の条件は未確認 | あいまい |
| 問い合わせまでの案内 | 商品ページの「質問する」ボタン | あり |
| 構造化データ | Organization のみ | あいまい |
| llms.txt | なし | なし |

6項目のうち、あり1・あいまい3・不足1・なし1。いちばん足りないのは、どんな体型・場面向けの服かを言う一文と、返品の条件が書かれていない点。
改善案（文そのもの）：
- h1：身長155cm 前後の人のための、丈直し不要のワンピース
- 説明文：（ブランド名）は、S〜L の3サイズで丈を短めに作るワンピース専門です。サイズが合わなければ、到着後14日以内に1回だけ無料で交換できます。
- 問い合わせまでの案内：サイズに迷ったら、身長と普段のサイズを送る。ボタン文言「サイズを相談する」
（丈の寸法と交換の条件は例。実際の値は持ち主に確かめる。）
先にやる1つ：返品・交換の条件を、商品ページの価格の近くに一文で書く。
引き継ぎメモ：
- 事業：ワンピースの通販
- 目標：サイズの相談から購入までを増やす
- 確認した数：6項目のうち不足1・あいまい3
- いちばんの問題：どんな人向けかと返品の条件が読めない
- 先にやる1つ：返品・交換の条件を価格の近くに書く
続けるなら：30日の集客改善（サイズ相談の件数と購入で確かめる）。

**旅（少人数の体験ツアー）**

受け取った情報：ツアーサイトの URL。h1 は「島であそぼう」、開催日と空きは別のページ、予約は電話とメールのみ、価格はページの画像の中にだけある。

| 項目 | 読めた事実 | 判定 |
| --- | --- | --- |
| 題と h1 | 「島であそぼう」 | あいまい |
| 事業内容の一文 | 読めない | 不足 |
| 価格と条件 | 画像の中のみ。文字では読めない | 不足 |
| 問い合わせまでの案内 | 電話とメールのみ | 不足 |
| 構造化データ | なし | 不足 |
| llms.txt | なし | なし |

6項目のうち5つが不足、1つがあいまい。いちばん足りないのは、価格が画像の中にあり、文字で読めない点。
改善案（文そのもの）：
- h1：定員6人の、島の朝カヤック体験（所要約2時間）
- 説明文：（ツアー名）は、初めてでも参加できる少人数のカヤック体験です。1人 6,600円（税込）、雨で中止の時は全額返金します。
- 問い合わせまでの案内：空きの日を見て、その場で申し込む。ボタン文言「空いている日を見る」
（金額・時間・条件は例。実際の値は持ち主に確かめる。）
先にやる1つ：画像の中の価格を、文字でページに書く。
引き継ぎメモ：
- 事業：少人数の体験ツアー
- 目標：予約の確定を増やす
- 確認した数：6項目のうち不足5・あいまい1
- いちばんの問題：価格が文字で読めず、予約の方法が電話とメールだけ
- 先にやる1つ：価格を文字で書く
続けるなら：30日の集客改善（空きを見てそのまま申し込める案内を置き、予約の確定で確かめる）。

### 決まり

- 持ち主への質問は、一度に1つだけ。
- この診断は何も送らない。結果は持ち主の手元に置く。
- 問い合わせの本文・連絡先などの個人の情報を、表に入れない。
- 数を推測で埋めない。読み取れなかったことは「未確認」。
- 件数や反応が少ない時の変化を、確かな効果として言わない。
- 成果を約束しない。

### 専門家の診断を受ける（選べる）

自分とエージェントで回すのに加えて、専門家に診てもらう道も選べる。Flapbase Cloud の Business に専任の支援担当者を追加すると、Flapbase で扱うサイト・SNS 投稿・Web 広告の診断と制作を支援してもらえる（https://flapbase.com/business）。
- このスキルの診断（AI 自身が答える）で直す点が多いとき、または直し方に迷うときに、**サイトの診断**を専門家に頼める。
持ち主にフォームを書かせない。診断に渡す材料は、Flapbase の中にすでに集まっている資料（プロジェクト概要・サイト・記事と投稿の記録・測定の記録）から組み、持ち主には「何を渡すか」を見せて承認してもらうだけにする。勧めるのは持ち主が迷ったときだけで、エージェントが勝手に申し込まない。

## チェックリスト

手順で確かめた項目を「確認済み」「未確認」「持ち主の判断待ち」に分けて書き出し、抜けがないかを確かめる。

## 終わりの目安

根拠のある診断と修正案、人が決める項目を返した。

flapbase-site-check で実装上の問題を点検する。

## Flapbase で続ける

[Flapbase で開く](https://flapbase.com/skills/site-diagnosis)。公開のスキルのページの「エージェントで使う」で、手順と使う道具を確かめて続ける。専用ワークフローや Project の自動作成はない。手元の結果は自動では送られない。続ける範囲と持ち込む材料を人が確かめてから進める。
